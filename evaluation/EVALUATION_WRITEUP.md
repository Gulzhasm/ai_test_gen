## 1. Evaluation overview

The framework is evaluated against the research questions defined in the project plan,
using the **production deployment** at the host organisation rather than a synthetic
benchmark. The system under evaluation is the hybrid test-case generation pipeline
(~70% deterministic rule-based expansion, ~30% LLM refinement using Google Gemini 2.5
Flash, grounded by RAG over ChromaDB and cross-validated by an LLM "Judge").

| RQ | Question | Metric | Study |
|----|----------|--------|-------|
| RQ1 | Does the tool reduce test-design effort and cost? | Time reduction, cost per test case | §5 |
| RQ2 | What is the first-pass structural quality of generated tests? | Deterministic clean-rate over a 996-case corpus | §3 |
| RQ3 | How completely and precisely do generated tests cover acceptance criteria? | AC-coverage recall / precision / F1 | §4 |
| RQ4 | What are the dominant failure modes? | Issue-category distribution | §3.3 |

The original self-healing locator objective is treated as **future work** (see §7); the
supervisor confirmed it is outside the dissertation's required scope.

## 2. Evaluation corpus

The evaluation corpus is the live test plan *SiteDraft / Phase 1* (Azure DevOps plan
`271600`, parent suite `284016`) for the **ENV QuickDraw** desktop CAD-style drawing
application.

- **55 user stories**, each represented as an ADO *requirement test suite*.
- **996 tool-generated test cases** comprising **8,152 test steps** (≈ 8.2 steps per test
  case, ≈ 18.1 test cases per story), spanning 7–61 test cases per story.
- Test cases were generated by the pipeline and reside in production, linked to their
  originating requirement — i.e. this is a real adoption setting, not a lab corpus.

This corpus (n = 996) is substantially larger than the pilot reported earlier in
development (n = 207, 12 stories), and directly addresses the small-sample limitation
noted in the pilot.

## 3. Study 1 — First-pass structural quality at scale (RQ2)

### 3.1 Method
Every test case in the corpus was retrieved from Azure DevOps (titles + steps), and
evaluated against the framework's **own deterministic quality contract**
(`core/services/test_validator.py::TestCaseValidator`) — the same rule set the
generator enforces at authoring time. A test case is **first-pass clean** if it raises
zero validator errors. The check is fully automated, requires no human judgement, and is
reproducible (§6). Two complementary clean-rates are reported:

- **Strict full-contract** — all rules, including the requirement that *every* test case
  contains an explicit pre-requisite step and a close/teardown step.
- **Content-clean** — excludes the pre-req/close *presence* convention, which is a
  suite-level pattern (follow-on test cases within a suite do not repeat setup/teardown)
  rather than a defect in the generated content. This rate isolates genuine content
  issues: forbidden/ambiguous language, missing expected results, and title-format
  violations.

### 3.2 Results

| Measure | Clean | Rate |
|---------|-------|------|
| Strict full-contract | 656 / 996 | **65.9%** |
| Content-clean | 877 / 996 | **88.1%** |

- Test cases flagged **only** for the pre-req/close convention: 221.
- Test cases with a genuine **content** issue: 119 (11.9% of the corpus).

The content-clean rate (88.1%) exceeds the project's ≥80% target. The strict rate (65.9%)
is reported for transparency; the 22.2-point gap is attributable almost entirely to the
setup/teardown convention rather than to defective test content.

### 3.3 Failure modes (RQ4)

Issue occurrences across the corpus (a test case may raise more than one):

| Category | Count | Nature |
|----------|-------|--------|
| Close-step convention | 238 | Structural (no per-test teardown) |
| Missing pre-req convention | 183 | Structural (no per-test setup) |
| Missing expected result | 59 | Content |
| Title format | 54 | Content |
| Forbidden / ambiguous language | 7 | Content |

The dominant *content* failure mode is the missing-expected-result on functional steps,
followed by title-format deviations. Ambiguous language ("or", "if available", etc.) — the
risk most associated with LLM generation — is rare (7 occurrences in 996 cases), which we
attribute to the deterministic rules and the Judge cross-validation layer.

## 4. Study 2 — AC-coverage precision / recall / F1 (RQ3)

### 4.1 Method
Structural cleanliness (Study 1) does not establish whether the generated tests actually
*cover the acceptance criteria*. Study 2 measures this against a human-authored ground
truth, at the granularity of acceptance criteria (AC):

- **AC Recall (completeness)** = in-scope ACs covered by ≥1 valid test ÷ total in-scope ACs
- **Test Precision (signal)** = generated tests mapping to ≥1 real AC ÷ total generated tests
- **F1** = harmonic mean of the two

The ground truth is light to author and independent of the tool's own claims: for each
test case, a single annotator records which AC id(s) it genuinely verifies (`covers: []`
marks a spurious/out-of-scope test). Acceptance criteria are taken verbatim from the ADO
user stories; no manual test suites are written.

### 4.2 Sampling
A **stratified purposive sample of 8 stories** was drawn from the 55-story corpus to span
test-suite size, AC count, and feature type:

| Story | Tests | ACs | Category |
|-------|------:|----:|----------|
| 269496 Model Space & Canvas | 7 | 4 | Display / initial layout |
| 271307 File – New Document Dialog | 10 | 8 | File operation |
| 270457 Zoom Controls (Keyboard & Mouse) | 12 | 10 | Input / interaction |
| 271053 Error Handling | 19 | 10 | Error / negative paths |
| 270472 Mirror Tool | 24 | 6 | Transform tool (high test:AC) |
| 270739 Properties Panel – Design | 32 | 9 | Properties panel |
| 270479 Basic Shape Tools | 51 | 9 | Core drawing tool |
| 273567 Interface – Top Menu Toolbar | 61 | 4 | Interface chrome (precision stress) |

This subset comprises 216 test cases and 60 acceptance criteria across eight distinct
feature categories, including two deliberate stress cases: a high test-to-AC ratio
(Mirror Tool) and an extreme ratio (Top Menu Toolbar, 61 tests / 4 ACs) that probes
whether the generator over-produces low-signal tests.

## 5. Study 3 — Effort and cost (RQ1)

Carried forward from the development-phase metrics report (Gemini 2.5 Flash):

- **~92% reduction** in test-design time (≈ 69 hours manual → ≈ 5.5 hours assisted for 207
  test cases in the pilot).
- **≈ $0.002 per test case** in LLM cost.
- **≈ 2.3×** acceptance-criterion-to-test-case amplification.

(These figures should be re-derived over the full 996-case corpus for consistency with
Studies 1–2; the pipeline logs token usage and latency via
`core/services/metrics/`.)

## 7. Threats to validity

- **Single annotator.** AC-coverage labels are produced by one researcher (who also built
  the tool). Mitigation: a second labeller on a subset for inter-rater agreement is
  recommended; AC text is objective and taken from ADO, reducing label subjectivity.
- **Structural ≠ functional.** Study 1 measures structural conformance, not bug-finding
  effectiveness. Study 2 measures requirement coverage, not defect detection.
- **Single model / domain.** All generation used Gemini 2.5 Flash on one application
  (ENV QuickDraw). Results may differ for other models or domains.
- **Convention vs defect.** The strict/content-clean distinction (§3) is a reporting
  choice; the dual reporting is intended to make it transparent rather than to inflate the
  headline figure.

## 8. Out of scope / future work

The self-healing locator subsystem (embedding-based re-matching + deterministic locator
re-authoring, no LLM) is designed but deferred; the captured UI element inventory already
provides its baseline store. Likewise, the executable-script half of Phase 2 (grounded
Playwright generation and a Page Object Model project) is implemented and demonstrated but
is presented as an engineering contribution rather than an evaluated study here.
